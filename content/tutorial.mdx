# Zero-Effort Regression Testing in Go: Turning API Traffic into Golden Master Tests with Keploy

Writing unit and integration tests for Go microservices is notoriously tedious. You define table-driven test cases, configure `httptest.Server`, write custom transport round-trippers, mock SQL drivers, and manually construct stub JSON responses. The moment your upstream dependencies change or your serialization schema updates, half your tests break—not because your business logic failed, but because your mocks drifted from reality.

**What if you could turn real API traffic directly into regression tests and self-healing mocks?**

That is the core proposition of **Keploy**. Keploy intercepts incoming network calls and outgoing dependency calls transparently at the Linux socket layer using **eBPF (Extended Berkeley Packet Filter)**. It records the interaction into readable YAML test files, and replays them in an isolated test runner where every third-party service is deterministically mocked.

In this tutorial, we will take a real Go application that fetches data from an external API, record real-world interactions, inspect the generated golden master test cases, replay them without hitting any live endpoints, and witness Keploy catch a real regression in action.

## What We're Actually Doing

To understand Keploy, you need a mental model of where it sits during development:

<ArchitectureDiagram />

### Traditional Testing vs. Keploy Workflow

* **The Traditional Go Workflow**: Write endpoint &rarr; start dependencies &rarr; fire curl to test &rarr; manually write `_test.go` with mock structs &rarr; update mocks whenever dependencies change.
* **The Keploy Workflow**: Run application under `keploy record` &rarr; fire natural curl requests &rarr; Keploy captures request/response pairs and dependency calls &rarr; run `keploy test` to replay and assert against the golden master.

<WhyItMatters concept="Zero Code Intrusion">
Notice that Keploy requires <strong>zero changes to your Go code</strong>. You do not import a Keploy SDK, you do not wrap your HTTP handlers in custom middlewares, and you do not pass mock context structs. Keploy operates purely at the OS network interface level.
</WhyItMatters>

## Prerequisites

Before starting, ensure your local environment satisfies the following requirements:

* **Go Compiler**: Go `1.20` or higher installed (`go version`).
* **Linux Kernel or WSL2**: Linux kernel 5.10+ (Ubuntu 22.04+ recommended) with `tracefs` / `debugfs` mounted. Windows developers can run seamlessly inside WSL2.
* **Keploy CLI**: Keploy v3.6+ installed.
* **cURL**: Standard HTTP command line client.

<Callout type="tip" title="Windows Developers Note">
Keploy's core engine relies on Linux kernel eBPF tracepoints (`sys_socket`). On Windows machines, run Keploy inside a WSL2 Ubuntu distribution. We documented how to set this up smoothly in the troubleshooting section below.
</Callout>

### What Just Happened Under the Hood?

Let's unpack what Keploy did during those startup logs:

1. **eBPF Socket Hook**: Keploy attached tracepoints to the Linux kernel socket subsystem (`sys_socket`).
2. **Virtual DNS Server**: Keploy started a local DNS listener on port `26789` to intercept domain name lookups (e.g. resolving `pokeapi.co`).
3. **Ingress Forwarding**: Keploy took control of port `8080` and established a transparent proxy to the application's internal listening socket.
4. **App Execution**: It executed the command passed via `-c` (`./http-pokeapi`) as a child process.

<Callout type="important" title="Flag Explanation: -c">
The <code>-c</code> (or <code>--command</code>) flag defines the exact command to start your application binary. Keploy manages the child process lifecycle, ensuring it is ready before accepting traffic.
</Callout>

### Anatomy of Keploy Artifacts

* **`spec.req`**: The exact inbound HTTP request captured from curl.
* **`spec.resp`**: The golden master response returned by your Go code, including status code, headers, and full JSON body.
* **`spec.assertions.noise`**: Look closely at `header.Date: []`. Keploy **automatically recognized** that the HTTP `Date` header changes on every execution and classified it as noise! You never have to manually ignore timestamps.
* **`mocks.yaml`**: Contains every external dependency call made while handling that request. When replaying, Keploy simulates PokeAPI entirely from this file.

<section id="things-that-surprised-me">
## Things That Surprised Me (DevRel Insights)

When running Keploy in a real developer environment, a few nuanced behaviors emerged that every engineer should know:

### 1. Windows Defender Flags Raw Binaries
When downloading the enterprise Windows executable directly, Windows Defender flagged it due to low-level packet capture drivers.
* **Resolution**: On Windows workstations, running Keploy natively inside **WSL2 (Ubuntu 22.04 LTS)** avoids antivirus false positives and gives first-class eBPF kernel support.

### 2. The `musl` vs `glibc` Gotcha
Keploy's network agent is dynamically linked against `glibc`. Running Keploy on minimal Alpine Linux distros triggers:
`cannot load agent: No such file or directory`.
* **Resolution**: Use glibc-based environments like Ubuntu, Debian, or Fedora.

### 3. Mounting `tracefs` in WSL2
eBPF tracepoints require `tracefs` to be mounted at `/sys/kernel/tracing`. In fresh WSL2 environments, mounting it takes one quick command:
```bash
sudo mount -t tracefs nodev /sys/kernel/tracing
```

### 4. Automatic Noise Classification
We didn't configure a noise rule for the `Date` header. Keploy automatically detected that `Date` is volatile and excluded it from failing the test suite.

<section id="troubleshooting">
## Troubleshooting Guide

<Callout type="warning" title="neither debugfs nor tracefs are mounted">
**Symptom**: <code>failed to attach the tracepoint hook on sys_socket: neither debugfs nor tracefs are mounted</code><br/>
**Fix**: Mount tracefs in your Linux/WSL terminal:
<pre><code>sudo mount -t tracefs nodev /sys/kernel/tracing
sudo mount -t debugfs nodev /sys/kernel/debug</code></pre>
</Callout>

<Callout type="warning" title="Port Already in Use (8080)">
**Symptom**: <code>listen tcp :8080: bind: address already in use</code><br/>
**Fix**: Ensure no old application instances are running in the background:
<pre><code>sudo fuser -k 8080/tcp || pkill -f http-pokeapi</code></pre>
</Callout>

<Callout type="warning" title="Replay Times Out / App Starts Slowly">
**Symptom**: Keploy attempts to send requests before the Go server finishes booting.<br/>
**Fix**: Increase the <code>--delay</code> flag (e.g. <code>keploy test -c "./app" --delay 10</code>) to grant additional startup headroom.
</Callout>

</section>

## Going Further with Keploy

Now that you have your first passing test suite, here are powerful next steps for your Go projects:

1. **Commit `keploy/` to Git**: Store your test cases and mocks alongside your source code as living API contract documentation.
2. **Integrate into GitHub Actions**: Run `keploy test` in CI so every pull request is automatically verified against real user traffic.
3. **Database Mocking**: Keploy natively intercepts MongoDB, PostgreSQL, MySQL, and Redis protocol traffic without requiring mock database drivers.
4. **Export to Postman**: Use `keploy export` to generate Postman collections directly from your recorded traffic.
